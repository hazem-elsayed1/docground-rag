# Citation review and provider outage protocol

## Evidence review

DocGround records three distinct properties of a generated claim.

| Property | How it is established |
|---|---|
| Citation provenance | The chunk ID and document revision match a chunk actually supplied to the model. The server resolves the source, section and URL from that chunk. |
| Quote validity | The exact quote occurs once within a single source field. The server resolves absolute document offsets. Repeated passages require additional surrounding words. Short unique quotes still require semantic review. |
| Claim support | A reviewer reads the supplied context and checks all premises, qualifiers and inferences. The application labels every generated claim as unreviewed until such an evaluation. |

A quote can be authentic and irrelevant. Review each claim and each associated citation separately. A citation supports a claim if it supplies a material premise for that claim. Set `adequately_cited` only when its citations collectively establish the full claim. If the claim is supported elsewhere in the supplied context, it can be `supported` without being `adequately_cited`. Judge answer correctness against the approved development questions and reviewed answer references. Resolve reviewer disagreements before publishing results.

The builder records candidate and included counts, included IDs, dropped IDs, exclusion reasons and UTF-8 byte budget. Citations can only resolve to included context. Empty selected context abstains locally. In development review, `approved_units_in_context` is computed from the included chunk IDs and approved full-span containment. Coverage, generated answers and model abstentions are three separate observations. Context missing a required unit warrants human scrutiny even when quotes validate. The application does not have reference answers for arbitrary user queries.

The system prompt and user payload occupy separate roles. Document instructions and adversarial user text stay in the user payload. The model has no tools. Local validation rejects invented citations and the UI shows generic errors for unexpected exceptions. An attacker may still induce a misleading claim with a genuine quote or a false abstention. Offline transport tests verify role separation and fail-closed citation handling. Live model obedience, contradiction handling and attack success rates are pending.

## Controlled development evaluation

Use a clean source checkout and a Google Developer API key from an explicitly verified Free Tier project with billing disabled. Confirm eligibility and quota in Google AI Studio. Set `DOCGROUND_FREE_TIER_CONFIRMED=true` only after that check. The collector reads the configured model and verifies `generateContent` availability through a model metadata request. It cannot infer billing or remaining quota from model metadata. It sends only the fixed, approved development questions and public documentation. Keep the attempt journal local.

Run `python -m scripts.evaluate_generation collect`. The journal `.local/generation/attempts.jsonl` binds the code, input hashes, model and prompt to each attempt. The prompt identity is `prompt_version` with the SHA-256 of the exact system instruction (`prompt_sha256`) and of the structured-output schema sent with it (`response_schema_sha256`). A change to the instruction, schema or evidence payload format needs a new `prompt_version`, and `tests/test_prompt_contract.py` enforces this. It saves request context, retrieved chunk IDs, raw model response when available, parsed claims and citations, usage, timings and sanitized errors. Preflight failure exits before any generated answer or attempt journal is created. A provider failure during collection stops the batch and retains the attempted prefix. Provider failures are authentication, permission, rejected or rate-limited requests, server errors, transport failures, local request errors and unreadable or malformed responses, all recorded as `provider_error`. A success response is malformed when its body is not a JSON object with `candidates` or `promptFeedback`, or when its first candidate has neither content nor a finish reason. Only HTTP 429, 500, 502, 503 and 504, and timeouts, network and proxy failures and server protocol breaks are marked retryable. Local request errors, redirect loops and undecodable or malformed bodies are not. `BLOCKED_REASON_UNSPECIFIED` does not count as a block. Output truncation (`response_truncated`), a provider content block (`content_blocked`) and a finished response without answer text (`empty_response`) are final outcomes for that question, and collection continues with the next one. User-visible errors and the error fields of journal records contain no provider error text, prompts or credentials.

After the outage clears, continue the same journal with `python -m scripts.evaluate_generation collect --resume`. Resume sends only questions with no recorded start, in the approved order, and stops again at the next provider failure. It never resends a completed result, a recorded failure or an interrupted attempt. Repeat `--resume` until every question has a recorded start. A later `--resume` then sends no generation requests and leaves the journal unchanged. Recorded eligible failures stay under the separate `collect --retry-failed` policy. A single run uses either `--resume` or `--retry-failed`, never both. Both require the existing journal, the lock to be free, every record to be intact and the same run identity. The identity is the complete journal header, including code revision, inputs, model details, prompt and configuration. Every `collect` invocation, including `--resume` and `--retry-failed`, first sends one model metadata request. Its result is part of the run identity, so it runs before the lock and journal are checked. A locked or damaged journal or a changed identity therefore stops the run after that metadata request, before any generation request, and leaves the journal unchanged.

Complete `.local/generation/review-template.json` as `review.json`. Retain the journal digest. The `claims` array follows the recorded claim order and each `citation_support` array follows its citation order. Fill `correct`, `supported`, `adequately_cited` and citation support with explicit booleans. Run `python -m scripts.evaluate_generation score`. Complete or partial results identify their attempted and scorable counts separately. The scorer excludes missing rows and failures from answer and abstention metrics. It reports failure counts by code, including truncation, invalid citations and provider failures. Initial and final failure rates describe attempted items. Report unattempted questions separately. Review dependent quality metrics only alongside these denominators.

The scorer has two reporting limits. `total_tokens` sums the usage of the last recorded attempt for each attempted question. That includes a failed final attempt when it has usage data, as malformed responses and invalid citations do. Attempts superseded by a retry are excluded. The total is null when any last attempt lacks usage. Provider errors, truncated responses, content blocks and interrupted attempts record none, so a run with any of these as a last attempt reports null. `mean_end_to_end_ms` is the only latency figure. It averages the last attempts of scorable questions and excludes failures. The journal records `retrieval_ms`, `generation_validation_ms` and `end_to_end_ms` for each finished attempt. An interrupted start has no finish and therefore no final timing. The scorer reports no timing split or percentiles. Report any token or latency figures derived from the journal separately from scorer output and state their denominators. Score each journal on its own. Runs under earlier prompt versions, including `grounded-claims-v2`, are historical and are never pooled with later results.

## Groq development collection

Groq is an evaluation-only alternative to Gemini. The Streamlit app does not use it. Pass `--provider groq` to `collect` and `score`. Without the option, every command keeps the Gemini behavior and paths described above. Groq uses `openai/gpt-oss-20b` through Groq's OpenAI-compatible chat completions endpoint. Use a key from a confirmed Groq Free Plan project with no paid plan or billing change. Set `GROQ_API_KEY` and `DOCGROUND_FREE_TIER_CONFIRMED=true` in the process environment or the local `.env` file. The collector sends the same v3 system instruction, strict response schema, evidence payload, retrieval settings, 16,000-byte evidence budget, temperature 0 and 4,096-token completion cap.

The Groq journal, review template and completed review live in `.local/generation/groq/`: `attempts.jsonl`, `review-template.json` and `review.json`. Its header adds `provider`, `provider_endpoint`, `request_format`, `min_request_interval_s` and `timeout_s` to the fields of a Gemini header. `model` is `openai/gpt-oss-20b` and `model_details` come from the model listing that preflight reads. The scorer refuses a journal recorded by another provider. A Gemini journal therefore can never continue or stand in for a Groq run, or the reverse. Score each provider's journal on its own and never pool their results.

Each attempt sends one HTTP request with automatic retries disabled. The outcome classes, retry eligibility and stop-on-outage behavior match Gemini. HTTP 429, 500, 502, 503 and 504 and transient transport failures stop the batch and are eligible for the one explicit retry. Authentication, other HTTP errors, local request errors and malformed or unreadable responses stop the batch and are never retried. A response that Groq rejects with error code `json_validate_failed` is a final `malformed_response` for that question, and collection continues. Errors and logs carry status codes, class names and known labels only, never provider text.

Within one invocation, Groq generation requests start at least 75 seconds apart. The interval is measured from the previous request's actual start. The collector waits under the journal lock before writing each start checkpoint, so the wait is not part of recorded latency. An interruption during the wait leaves that question with no recorded start, and `--resume` sends it later. The pacing keeps a near-limit request of about 5,100 tokens, measured with synthetic evidence at the 16,000-byte limit, under the documented Free Plan limit of 8,000 tokens per minute. A full 24-question run takes about 30 minutes. Pacing does not carry over between commands. Wait at least 75 seconds after the last request of one command before starting `collect --provider groq --resume` or `--retry-failed`. After a 429, also wait for the time the account's rate-limit status shows before continuing.

The daily token limit is a separate check before live collection. Pacing does not enforce it. Before starting, confirm the account's current daily token limit and remaining allowance on the Groq console Limits page. Budget about 6,500 tokens per attempted question, or about 160,000 tokens for the 24 questions. Allow for up to one retry per eligible failure. If the remaining allowance is lower, do not start. A run that stops on a 429 has used its first attempt for that question and can be retried only once.

## Recovering a development journal

Each start and finish is appended as one UTF-8 JSON line. The writer flushes and syncs the start before executing the request and the finish before moving to the next question. A complete start with no finish is an interrupted attempt. Its remote outcome is unknown and it is ineligible for retry or resume. Questions with no start remain unattempted, and only they are eligible for resume.

The steps below use the Gemini paths. For a Groq run, the journal, lock and review files are `.local/generation/groq/attempts.jsonl`, `.local/generation/groq/attempts.lock`, `.local/generation/groq/review-template.json` and `.local/generation/groq/review.json`. Score it with `python -m scripts.evaluate_generation score --provider groq`. Continue it only with `collect --provider groq --resume` or `collect --provider groq --retry-failed`.

1. Stop collection and confirm that no process can still write this journal. An `attempts.lock` file blocks collection, retry and resume. Its age does not establish that it is stale. Keep the lock while a writer is active or its status is uncertain.
2. Preserve private, byte-for-byte copies of `attempts.jsonl`, the lock if present and the associated review files. After confirming that no writer remains and preserving the lock, move the stale lock out of the way. Never clear an active lock.
3. Inspect a copy offline. An unterminated final record is rejected even when its JSON text parses. If the final line alone is unterminated, use a separate scoring copy containing the bytes through the last LF, including that LF. Keep the original intact. If there is no complete header or validation still identifies invalid JSON or an invalid event, stop and investigate the original. Keep complete start records and leave unknown outcomes interrupted. Do not fabricate finish records or retry flags.
4. Use any repaired copy for offline review or scoring only. Validate it with `src.checkpoints.read_journal` and use it as `.local/generation/attempts.jsonl` in an isolated offline checkout for `score`. For a Groq journal, use `.local/generation/groq/attempts.jsonl` and `score --provider groq`. Recheck the retained judgments and bind the review to the repaired copy's SHA-256. The scorer parses and hashes one byte snapshot. Report exclusions and unattempted items with the partial result. A repaired prefix cannot authorize provider retries or a resume because its omitted tail may have changed what was attempted. Never copy a repaired prefix back over the original journal path.
5. Only an intact original journal under the same run identity can authorize an explicit retry of a recorded eligible failure under the existing policy, or a resume of unattempted questions. An unfinished or uncertain attempt remains ineligible, even after clearing a stale lock. A change of code revision changes the run identity.

## Pre-registered future holdout policy

1. Secure separate owner authorization and lock the code, provider model identity, evaluation split, retrieval and context settings, prompt, rubric, outage rules and retry eligibility before accessing holdout material. No holdout run happened in this milestone.
2. Persist a start checkpoint before each generation request and a finish checkpoint after it, keyed by question and attempt. Flush and sync both. Preserve model refusals and validated answers as final outcomes with zero retries.
3. Disable automatic SDK retries in evaluation. Permit at most one explicitly authorized retry for a recorded transient HTTP 429, 500, 502, 503 or 504, or a transport timeout or failure. Retry failed IDs only. Authentication, malformed or truncated model responses, invalid citations, interrupted attempts with unknown remote status and inconvenient answers are ineligible. Development uses `collect --retry-failed` to authorize eligible retries against the identical journal configuration. It never retries previously successful or unattempted items. Development `collect --resume` sends only items with no recorded start under the same identity. Whether a holdout may resume after an outage needs its own owner decision before the holdout is locked.
4. Preserve both original and retry outcomes and their timing. Separate service failures, validation failures, interruptions, unattempted items, model refusals and local no-context abstentions. A hard process death can leave a lock or torn final record. Preserve the original journal for inspection and reconcile it before further work. Never automatically resend an ambiguous request.
5. Report first-attempt and post-retry availability separately from answer quality. If an outage prevents a complete holdout, mark the evaluation partial and state what was unavailable before releasing metrics. Keep private per-item results outside any public report. The development collection code does not accept an arbitrary split path.
